# Architecture

How the parts fit together and where to look. The reasoning behind the choices, with the measurements that settled them, is in [DESIGN.md](DESIGN.md); the rules an agent working here has to respect are in [CLAUDE.md](CLAUDE.md). This file is the map.

Written with [Claude Code](https://claude.com/claude-code).

## In one sentence

A static site serving a curated corpus of PDFs, searchable in natural language across the whole corpus, where a query costs one POST to the site's own small search service, which embeds the question through an encoder shared with a sibling project and dot-products it against an index it keeps resident: the reader's browser downloads no vectors and ranks nothing.

The software and the corpus are separate. Every `data/...` and `dist/...` path below is resolved inside `$CORPUS_DIR` (`scripts/lib/corpus.py`, `server/lib/corpus.mjs`), which is required and has no default. What a corpus configures (facets, vocabularies, tiers, renditions, languages, figures, OCR, manifest columns, the judge's task) lives in `$CORPUS_DIR/corpus.toml`; [corpus.example/corpus.toml](corpus.example/corpus.toml) documents every key and is what the test suite runs against.

## The shape of the thing

```
$CORPUS_DIR/data/GUIDELINES/        the only servable corpus
  |
  | scripts/check_pdfs.py           hard gate: every file is a PDF a browser opens
  | scripts/manifest.py      -> data/MANIFEST.tsv       per-document metadata, blanks only
  | scripts/ocr.py           -> data/OCR/               text layers for scanned pages
  | scripts/chunk.py         -> data/chunks/            text + page + bounding boxes
  | scripts/verify_chunks.py        hard gate: nothing skipped, no undrawable box
  | scripts/embed.py         -> data/vectors/<bake>/    one .npz per document, fp32, unit-norm
  | scripts/build_index.py   -> dist/index/             FULL index: 1 bit x 1024 dims, page
  |                                                     vectors, chunk table, per-document text
  | scripts/stage.py         -> dist/www/               OPEN PDFs (symlinks), the site, MANIFEST.tsv,
  |                          -> dist/restricted/        changelog.json, app-version.js, and index/
  |                                                     as symlinks to its PUBLIC half. RESTRICTED
  |                                                     documents go to the SIBLING directory, with
  |                                                     their chunk text stripped
  | scripts/check_served.py         hard gate: no restricted document, no word of one, in dist/www/
  | node scripts/check_search.mjs   hard gate: the shipped ranker against the real index
  v
deploy (rsync of dist/, docker/, server/, the src/ modules the search image copies)

  browser --GET--> web (Caddy, read-only, 127.0.0.1:8648)  dist/www at /srv
     |
     +--POST /api/search------> search:8650 (server/service.mjs, dist/index at /index,
     |                            nothing published on the host)
     |                              |
     |                              +--> the encoder container, over the external
     |                                   EMBED_NETWORK (default justeles-embed)
     |
     +--GET /api/page?doc=&p=--> pages:8651 (server/pages.py, dist/restricted at /restricted,
                                   cuts ONE page out per request)
```

Every step is content-hash gated, so re-running the chain with nothing changed takes under a minute. The gate for the expensive step is the `src_hash` in each `.npz`: the chunk texts plus the model identity, the chunking parameters, the weights filename and a format version.

## Build pipeline

**`scripts/manifest.py`** maintains `data/MANIFEST.tsv`, one row per document. It fills blank cells and never overwrites a curated value, so it is safe to re-run after hand-editing. Two columns drive behaviour rather than display: `family` groups the renditions of one document, and `rendition` says which kind each is (vocabularies in `corpus.toml` `[renditions]`). Facet columns may be multi-valued: they hold `VALUE_SEPARATOR`-separated slugs drawn from the closed vocabularies in `corpus.toml`, and `check_vocabulary` refuses to write a manifest naming a slug outside them. One column is graded rather than tagged: the tier column (`[tiers] column`) holds a single tier, derived from the vocabulary column `[tiers] derived_from` where a curator left it blank. Neither family nor rendition can be guessed from a file, so the TSV is their only home. Two optional curated tables override guesses: `data/CURATED_FAMILIES.tsv` supplies family and rendition, and `data/CURATED_ISSUERS.tsv` overrides the issuer patterns for documents where a pattern matched a citation rather than the publisher. Two columns are read out of the PDF rather than guessed from its filename: `doi` and `isbn`, the identifiers a document prints about itself, which the site turns into links. They carry their own marker, `NO_IDENTIFIER` (`-`), because a blank cell alone would mean both "nobody looked" and "there is nothing there", and the scan costs as much as the rest of the script: blank first, `-` second, `--rescan-identifiers` looks again. A cell holding a real identifier is never re-read.

**`scripts/ocr.py`** writes `data/OCR/` for documents with scanned pages and no text layer (`--dry-run` counts them). The derivative, not the original, is what gets served, because highlight coordinates only mean something in the file they were computed from. `data/OCR/ocr_index.json` records, per copy, the sha256 of the original it was made from, and `chunk.py` uses a copy only while that digest matches the original on disk: a replaced original makes the run refuse with a "re-run ocr.py" message instead of chunking a stale copy. A copy whose original left the corpus is deleted on the next run.

**`scripts/chunk.py`** writes one JSON per document: chunks of 170 to 512 tokens, cut at a section boundary once 170 are behind it, each carrying its text, the pages it spans and its highlight boxes in PDF points, grouped by page. Two packing variants exist for experiments: `--boundaries` ends chunks at paragraph, list, heading and page breaks instead of wherever the token budget runs out, and `--page-chunks` makes one chunk per page (the page bake). DESIGN.md, "chunks that end where the text ends", has what they measure. A chunk's text keeps the shape of the page it came from: a newline in front of a row that starts a block, and in front of a row whose predecessor ended short of the margin, so a list of short items does not arrive as one long line (DESIGN.md, "chunk format 14"). A table is read out cell by cell, from pymupdf's ruled-line detector or, for a table ruled only around its header, from the grid the `pymupdf-layout` model predicts; those grids are cached per PDF under `data/private/layout/` because the model costs about a second a page (DESIGN.md, "chunk format 15"). Each chunk file records `"source": "ocr"` or `"original"`, the single definition of which file gets served.

It also appends one chunk per figure that `scripts/figures.py` has a description for, read back through `scripts/lib/figure_record.py`: the text is a vision model's description of the figure, the one box is its crop, and the chunk carries a `figure` field (model, kind and language) that `build_index.py` passes into the per-document JSON so the page can say the text is a model's and not the document's. `embed.py` reads the kind and language to open the encoder's input with a word such as "Tableau : " or "Flowchart: " between the metadata label and the description, without changing the text the reader sees. Figure chunks always come last in a document, which `build_index.py` checks, so `meta.json` records only a per-document `figure_count`, and the figures filter (`figures: include | exclude | only` on `POST /api/search`, the "Figures" selector on the page) is a cut of the document's chunk range in `rank()` rather than a per-chunk flag. Descriptions are folded into a document's content hash only when it has some, so a new batch rechunks and rebakes only its own documents (DESIGN.md, "Figures are searched through text instead"). `scripts/verify_chunks.py` refuses a corpus with a skipped PDF, an empty document or a box outside its page.

The chunker's code is split by stage, with `chunk.py` keeping the command line, the content-hash gate and the worker pool: `scripts/lib/chunk_glyphs.py` turns glyphs into lines, `chunk_extract.py` and `chunk_tables.py` read the page, `chunk_text.py` mends the text (hyphens, spaces, line ends), and `chunk_pack.py` packs rows into chunks. `chunk_row.py` holds the `Row` they all pass along. Every setting that changes what comes out travels in one frozen `ChunkSettings`, whose `params()` is exactly what the content hash covers, so a new setting cannot reach the chunker without also reaching the hash. `tests/test_chunk_golden.py` pins the hash and the chunk output for the defaults and every grid strategy.

**`scripts/embed.py`** encodes chunks with the shared encoder's model (currently `jinaai/jina-embeddings-v5-text-small-retrieval`) in ONNX into `data/vectors/<name>/`, at the model's full 1024 dims, L2-normalised. The encoder code is the sibling's (`../justelesRCP/src/onnx_embed.py`), so the passage prefix, the pooling and the int8 weights are defined once for both sites. Three properties cost hours when guessed wrong, and CLAUDE.md lists them: it holds an exclusive `flock` on its output directory, `--threads 0` means one thread per physical core (taking every hardware thread instead is 3.3x slower), and `--weights model.onnx --gpu` bakes in minutes instead of hours but is not the weights the server answers queries with. Each `.npz` also records `chunks_hash`, the `src_hash` of the chunk file it was baked from, and `build_index.py` refuses a bake whose `chunks_hash` disagrees with the chunks on disk or is missing. `embed.py` counts a file without that field as stale, so an older bake is rebaked by an ordinary run rather than refused by a step that cannot fix it.

**`scripts/build_index.py`** turns one bake into `dist/index/`. It truncates to 1024 dims and, at the `--quant binary` it ships with, keeps one bit per dimension, the sign of each component, packed eight to a byte. `--quant int8` writes the same index at a byte per dimension instead, and `src/search.js` reads either: which one ships is a cost decision, re-taken each time a corpus changes size (DESIGN.md, "binary is what ships"). At a given byte budget, dimensions are worth more than precision (DESIGN.md, "spend the bits on WIDTH"). `meta.json` publishes an allow-list of manifest columns (`PUBLIC_COLUMNS`), never the whole row: a manifest column in neither the public nor the private list stops the build rather than shipping by default.

**`scripts/stage.py`** assembles `dist/www/`, the tree Caddy serves: the servable PDFs as symlinks (so `dist/www/` costs nothing locally and `rsync -L` sends real files), `MANIFEST.tsv` as a copy, `src/` flat at the root, and `vendor/` as a directory. It prunes what it no longer stages, driven by its record in `.stage-manifest.json`. It links the PUBLIC half of the index into `dist/www/index/` (`meta.json` and `meta.json.gz`, relative symlinks into `../../index/`). The vectors are not linked at all, so no Caddy rule has to hide them.

It is also where the `access` tier is enforced, which is the only place it can be. The manifest grades every document `open` or `restricted`, and a restricted one may be read a page at a time but never handed over whole. The front end acts on the tier but cannot enforce anything: a browser can address any URL. So `stage.py` sends restricted documents to `dist/restricted/`, a SIBLING of `dist/www/` rather than a child, which makes them unaddressable: no Caddy root reaches outside its own tree. Per-document JSON is published file by file rather than by linking the directory: whole for an open document, and with every `text` field dropped for a restricted one, which leaves the page numbers and boxes the viewer needs. Both halves are then checked rather than trusted, by the gate below.

**`scripts/check_served.py`** refuses a staged tree that holds a restricted document or a word of one. It walks `dist/www/` by filename (symlinks count, since `rsync -L` turns them into files) and reads back every `index/doc/*.json` and `.json.gz` to confirm the restricted ones carry no chunk text. It runs after `stage.py`, because what it watches is a property of the staged tree rather than of the code that wrote it.

**`scripts/changelog.py`** compiles the release notes into `dist/www/changelog.json` (plus a zeroed-mtime `.gz` for Caddy), imported by `stage.py` rather than a step of its own, so no staged tree can carry stale or missing notes. The notes are `docs/changelog/<version>/changelog.md` with the root `VERSION`, or the corpus's own `$CORPUS_DIR/changelog/` and `$CORPUS_DIR/VERSION` when it ships them, which then replace the software's. It refuses when the version has no notes, when a file does not parse, or when a bullet lacks its French line. `stage.py` also writes `dist/www/app-version.js` from that version.

**`scripts/vendor.py`** fetches pdf.js from a pinned archive, verifies its SHA-256 and extracts an allow-list of members into `vendor/pdfjs/`. An allow-list rather than an exclude list, because the failure mode of a missed exclusion is shipping something.

## What `dist/index/` is

`scripts/build_index.py` writes the whole of it, and the search service reads it, mounted read-only at `/index`. `stage.py` links only `meta.json` and `meta.json.gz` into `dist/www/index/`, under the web root, which is a stronger rule than hiding: a hide rule fails open the day the index grows a file the rule does not name.

| File | Who reads it |
| --- | --- |
| `meta.json` | both: the page fetches it once for the document table and the facets, the service loads it at startup |
| `vectors-<hash>.b1` | the search service only, resident |
| `pages-<hash>.b1` | the search service only, resident |
| `chunks-<hash>.u16` | the search service only, resident |
| `refs-<hash>.u8` | the search service only, resident |
| `doc/<id>.json` | both: the service for the BM25 pass and snippets (cached, `SEARCH_TEXT_CACHE` documents), the viewer for one document's highlight boxes |

The vector file is one row per chunk of 128 bytes, one bit per dimension at 1024 dims (at `--quant int8`, 1024 bytes a row), most significant bit first, in document order. The page file holds one more row per page of the corpus in exactly that layout, which is where the 15% page term in the score comes from. The chunk file holds four little-endian `uint16` per row: the document id, the page the chunk opens on, the row its page occupies in the page file (0xFFFF when it has none, which happens on a page with boxes but no embeddable text), and the row its section occupies in an optional `sections-<hash>.b1` (format 4; the shipped index carries no section file and the slot is 0xFFFF throughout, because DESIGN.md measured that the section term found nothing to ship).

The reference file (format 5) holds one `uint8` per chunk, in the same order: how much the chunk reads like a citation list rather than prose, from 0 to 255, scaled so 255 is the corpus maximum, with `meta.json`'s `ref_scale` saying what cosine that maximum was. A request that asks for it has `REFERENCE_PENALTY` (0.30 of a cosine) times that fraction taken off every chunk's score, which pushes a bibliography below prose that cites the same words without hiding it. The axis it is measured against is mined from the corpus rather than written as a query: `build_index.py` averages the chunks that LOOK like citation lists (`looks_like_references`) and subtracts the mean of every chunk, leaving the direction the two differ in (DESIGN.md, "a reference penalty has to be mined from the corpus").

Every file name carries a content hash of its file, and `meta.json` names them rather than the client hardcoding them, which is what lets layout filenames change without an edit in `src/search.js`. `meta.json` is served `no-cache`, so a rebuilt index is picked up on the next visit; the pairing matters as much as the freshness, because `meta.json` holds the chunk offsets that index INTO the vector and chunk files, which are now only ever read on the server, where both halves come off one mount and cannot disagree. `meta.json` carries the format version, the width, the quantisation, the page weight, the two bake names, the document table (the public manifest columns plus `chunk_offset` and `chunk_count`) and the rendition-collapse policy.

The per-document text files hold each chunk's text, pages and boxes. They are the bulk of the index, and each side takes a handful of them: the service keeps the most recently used ones for the BM25 pass and result snippets, and the viewer fetches exactly one, for the document the reader opened. The deploy sends `dist/index/` once and the public half again under `dist/www/index/`. That is accepted on purpose: one copy shared by both would mean either serving the vectors' directory or pointing Caddy at a path outside its own root.

## Runtime, client side

`src/` has no framework, no bundler and no build step. Modules are loaded as ES modules directly. The page ranks nothing: it posts the question to `/api/search` and renders what comes back.

| File | Job |
| --- | --- |
| `index.html`, `app.js` | the search page: form, facet controls, corpus listing, result rows in either view, `?q=` URL state |
| `browse.html` | the document list: the same `app.js` and facets, no question and no search request |
| `search.js` | the whole ranking path: parse, load, embed, score, fold, group, browse, lazy text. It runs in BOTH places: the page imports `parseQuery`, `checkParsedQuery`, `loadIndex` and `searchRemote` from it, and the search service imports the ranking half of the same file |
| `view.html`, `viewer.js` | the hit viewer: pdf.js rendering with the matching passage highlighted (a button, or `h`, hides it so the page reads as published), a selectable text layer over the canvas, a click to fill the screen with the page, and one control handing over the whole PDF |
| `i18n.js` | French and English in one page, `data-i18n` bindings, the chosen language remembered through `store.js`; a corpus may overlay it with `$CORPUS_DIR/strings/<lang>.json` |
| `theme.js` | auto, light, dark |
| `tour.js` | the first-visit tour, pointing at real elements |
| `paths.js` | the URLs of the served PDFs and of the viewer's own downloads, written once |
| `prefetch.js` | a speculative download queue, one request at a time |
| `store.js` | `load` and `save` behind try/catch (a private window with blocked storage throws), every key under the prefix `<site id>.` from `corpus.toml` `[site] id`, with a one-time migration of the corpus's `legacy_keys` to their prefixed names so a returning reader keeps their choices |
| `app.css` | the palette, shared with justelesRCP |
| `app-config.js` | the local-development fallback for what the container renders from its environment |
| `site.js` | the chrome every page carries: metrics, development banner, footer |
| `changelog.js` | the "What's new" popup: fetches `changelog.json`, opens itself for a returning reader whose last visit predates a release, and opens on demand from the footer |

A query does this. `parseQuery` splits the box into the texts to embed (one, for an ordinary question) and `checkParsedQuery` refuses an empty or too-short question, both client-side, so a question that cannot be answered costs no request. What survives goes to `searchRemote`, one `POST /api/search` with `{ "q": "...", "filters": {...}, "bm25": false, "demote_references": true }`, which comes back as `{ "results": [...], "floor": ..., "dims": 1024 }`, each result carrying its document, chunk, page, pages, cosine, score, lexical score, `more`, `alternates` and text. `app.js` renders the list and nothing else: no vector matrix in the browser, no scoring loop and no client-side floor. The page's own `loadIndex(undefined, { vectors: false })` fetches `index/meta.json` alone, for the document table and the facets, which `browse.html` needs anyway. The viewer fetches `index/doc/<id>.json`, one document at a time, for the highlight boxes. The errors the page has to render are the service's: 400, 502 and 503.

Facets work like this. `facets()` collects the distinct values present in the corpus, splitting each cell on the separator `meta.json` carries, so `report;summary` contributes two options rather than becoming a third kind of document. `allowedDocs()` matches on ANY of a cell's values and knows three selection shapes: a string, an array and a `{from, to}` year range. A blank cell never satisfies an active filter. Option text comes from `i18n.js` under `facet_<field>_<slug>` and falls back to the slug itself, which `check_search.mjs` refuses to let happen for any shipped value.

Three behaviours are worth knowing before reading the code. Facets are derived data, so a manifest column nobody curated produces no control at all rather than an empty one, and each control offers its values as checkboxes, several at a time, ORed. A rendition name the policy does not recognise is never collapsed: showing one answer twice is untidy, while hiding the only document that answers a query is a broken search. The year range records a filter only once the reader narrows it, so a slider sitting at its full extent does not quietly drop documents whose year is blank.

The tier level is the exception to all that. The tier column holds one value of `[tiers] order` in `corpus.toml`, narrowest first, and `build_index.py` ships that order in `meta.json` so it exists in exactly one place. Two rules make it not a facet, and `matchesGuideline` in `src/search.js` holds both. Tiers are NESTED, so asking for the second tier keeps the first one too. And a BLANK cell PASSES, where a blank cell fails every facet: blank means nobody judged the document, which is not the answer the last tier records, and a facet rule would hide a corpus that is only partly curated without telling the reader. `app.js` renders the levels as a `<select>` at the head of the panel, defaults to all, remembers the reader's choice and writes it into the URL only when it differs from the default. The pre-push hook counts untiered documents and asks before pushing, since blanks are curation backlog rather than a broken tree.

## Runtime, server side

Three containers: all `read_only: true`, all run as the host uid rather than root (`APP_UID`/`APP_GID`), all `cap_drop: ALL`, all `no-new-privileges`, all with tmpfs for every writable path, each with a `mem_limit` and a `pids_limit`. `web` is Caddy on plain HTTP, TLS terminated upstream, with `NET_BIND_SERVICE` added back for the binary's file capability, `${DIST_DIR}/www` mounted at `/srv`, a strict `default-src 'self'` CSP with no CDN and no external font, and the only published port. `search` is the ranker, `server/service.mjs` under node:22-alpine with no npm install at all, with `${DIST_DIR}/index` mounted read-only at `/index`, listening on 8650 and never published on the host. `pages` is the third, `server/pages.py` under python:3.12-slim with pymupdf, with `${DIST_DIR}/restricted` read-only at `/restricted` and `${DIST_DIR}/index` at `/index`, listening on 8651 and never published either.

`GET /api/page?doc=<id>&p=<n>` answers a one-page PDF cut out of the file on the spot: `insert_pdf(from_page=n-1, to_page=n-1)` into an empty document, `tobytes(garbage=3, deflate=True)`, `Cache-Control: private, no-store`. mupdf opens a document lazily, so a page in the middle of a 1,275-page book costs about 4.3 ms and the page's own size rather than the file's. Two properties are deliberate and explained in the code. Document handles are kept in a small LRU (`PAGES_CACHE`, default 4), because reopening a large PDF per page turn would undo that. Every cut is serialised under one reentrant lock behind a bounded semaphore (`PAGES_CONCURRENCY`, default 2), because mupdf is not thread-safe and a small server has no cores to spare; the lock is reentrant because `cut_page` holds it and calls `open_document`, which takes it again, and a plain `threading.Lock` deadlocked the first request. A document is addressed by its index id, never by name, and the file the id maps to is checked to be a bare filename, so no `doc=` value can walk out of the mount.

There is no token on the endpoint, which is a decision rather than an oversight. A signed URL would stop nobody who could read one page from reading the next, since the viewer has to be able to ask for it; it would stop a link being shared, which is not the exposure. The exposure is the whole file in one request, and that is closed by the file not being there. What remains is a scraper willing to make one request per page against a rate-limited endpoint, which is a different and much smaller thing than fetching the PDF.

`search` is built from `docker/search.Dockerfile` with the REPO ROOT as context, because it imports `src/search.js`. That is only safe because the root `.dockerignore` denies everything and re-admits exactly `docker/`, `server/` and the named `src/` modules. `tests/search_image.test.mjs` rebuilds the file set the Dockerfile copies and `.dockerignore` admits, so a new import that forgets one of them fails the suite instead of the container: an exclude list here would fail open, and failing open means uploading a corpus that may never leave the build machine.

`server/` carries three services (the third optional). `server/load.mjs` loads the index under node through `server/lib/browser_shim.mjs`, which maps `globalThis.fetch` onto the filesystem so `src/search.js` runs unmodified. `server/queue.mjs` is a bounded serial queue: one worker ranks, up to `SEARCH_QUEUE_DEPTH` (default 24) searches wait behind it, and anything beyond is refused with 503 and `Retry-After: 2` rather than making everyone wait a second longer. Ranking is serial on purpose: the index is one buffer, and a second worker would halve its cache hits. A client that disconnects while queued is dropped without being ranked. The same bound covers the whole answer, not only the ranking: at most `SEARCH_QUEUE_DEPTH + 1` searches are in flight anywhere (waiting on the encoder, queued, ranking or reading text), and the next one is refused as `full` before it costs an encoder call. Numeric settings are validated at start, so a typo in `docker/.env` stops the service instead of turning the depth into NaN, which bounded nothing. `server/service.mjs` is the HTTP surface: it holds the index resident, plus a per-document text cache capped at `SEARCH_TEXT_CACHE` documents (default 64) for the BM25 pass and result snippets. It logs the status code and timing of a search, never the question. The container runs it with a 256 MB heap cap: without one, V8 lets the garbage from parsing per-document JSON grow past a gigabyte before collecting (DESIGN.md, "Measured: the ranking on the server").

The search API has two paths. `POST /api/search` takes `{ "q": "...", "filters": {...}, ... }` and answers the results, 400 for a malformed or too-short question, 502 when the encoder is unreachable, 503 when the queue is full and 500 on a width mismatch. `GET /api/search/health` answers `{ ok, dims, n_chunks, waiting, rss_mb, ranker_sha, index_sha }` and is also the container's healthcheck; it carries the index width and queue depth but no query text. `ranker_sha` is the first twelve hex characters of the SHA-256 of the `src/search.js` the process imported, taken once at startup: it is how a caller tells a service running the current ranker from one started before the last edit, which node cannot detect by itself because it caches an ESM import for the life of the process. `index_sha` is the same construction over the bytes of the `meta.json` the process LOADED, so a service holding a previous build is visible even when a rebuild left the chunk count alone, and even when it left every matrix alone (a metadata-only rebuild). `node scripts/check_search.mjs` with `SVC` set compares both. The page API has two more: `GET /api/page?doc=&p=`, answering `application/pdf` (404 for an unknown document or a page outside it, 503 when every cutting slot is busy), and `GET /api/page/health`, answering `{ ok, documents }`. Everything else under `/api/` is 404.

The ranking itself is `src/search.js`, the same file the page imports, running in the service. `embedQuery` posts the question to the encoder, asking for the index's width with `dim`, and gets a vector renormalised back onto a scale of 127, the only shape `rank` knows. `rank` scores every page vector once, walks the documents (so a filtered-out document's chunks are skipped in one test) and scores every eligible chunk as `0.85 * its own cosine + 0.15 * its page's`, keeping the best 300 in a bounded sorted array. When the request asks for it and the index carries a reference file, a chunk loses `0.30 * refs[c] / 255 * ref_scale` of a cosine in the same pass, before the floor is applied, so a bibliography needs a better match than prose to outrank it. When the request asks too, every passage of a document gains `0.05 * 0.5 ** ((newest year in index - its year) / 8)` of a cosine, computed once per document rather than once per chunk and added in the same place, before the floor: a guideline is written to be replaced by its next edition, and an embedding cannot see the year. Both are on unless the reader unticks them, and both are bonuses or penalties rather than filters, so an older or more citation-like passage that is genuinely the better answer still wins. The page weight comes from `meta.json`, so an index built with `--page-weight 0` turns the page term off without a code change.

The scoring is asymmetric: in the shipped index a passage is one bit per dimension while the query keeps its int8 precision, so the score is a sum of `+/-query[d]`, and the divisor that recovers a cosine is `127 * sqrt(dims)`. That is done through a table built once per query, holding what each of the 128 byte positions contributes for each of the 256 possible byte values, so a passage costs 128 lookups rather than 1024 multiplications; it is twice as fast to scan as a 256-dim int8 index of twice the size.

Then `rescore` reorders the top 50 by `cosine + 0.15 * bm25 / scale`, with BM25 computed over those 50 candidates' own chunk text and nothing shipped for it: no term statistics, no inverted index. `scale` is the best BM25 among the candidates written in the SAME language as the one being scored, floored at half the best in the whole shortlist (`LEXICAL_GROUP_FLOOR`), which `rank` makes possible by copying each document's `language` onto its candidates. One global scale made the term a vote for the reader's own language rather than a tiebreak, because the shortlist for a question in one language is mostly documents in that language, and those are the ones it shares words with; DESIGN.md, "BM25 was a same-language preference in disguise", has the measurement. It runs before folding, because folding picks which document in a family stands for the family. `scripts/evaluate_rescore.mjs` imports `src/search.js`, so what is measured is what ships. `foldResults` applies two different groupings: a family collapse, which hides a document behind another rendition of the same content, and a per-document cap of three passages, which stops long documents crowding out short ones. `SEARCH_FLOOR` is applied there, once, on the server, and the value used is echoed in every answer so the page can say "nothing above the floor" honestly. `attachText` fetches the text, first for the shortlist the rescoring reads and then for whatever survived folding.

`docker/Caddyfile` reverse-proxies exactly the two search paths to `SEARCH_UPSTREAM` (default `search:8650`) and the two page paths to `PAGES_UPSTREAM` (default `pages:8651`) over the compose default network, by service name, through Docker's embedded DNS, and answers 404 for everything else under `/api/`. The page never embeds a query itself, so this site opens no path onto another project's service, and `web` is not on the shared network at all. `/api/search` is rate-limited per IP at 60 requests a minute (`SEARCH_RATE_EVENTS`, `SEARCH_RATE_WINDOW`), and the body is capped at 16 KB at the edge as well as inside the service. Tight on purpose, for two reasons: the service ranks on one worker behind a bounded queue, so a flood from one visitor would answer 503 to every other, and every query it accepts goes on to the SHARED encoder. `/pdf/*` carries a second, looser zone at 300 a minute (`PDF_RATE_EVENTS`, `PDF_RATE_WINDOW`), which is the bandwidth limit rather than the CPU one: the documents are the only large responses this site serves, and pdf.js fetches each by HTTP Range, so one page costs several requests. `/api/page` carries a third zone at 120 a minute (`PAGE_RATE_EVENTS`, `PAGE_RATE_WINDOW`), between the two on purpose: a reader turning pages makes one request per page, so it cannot be as tight as search, and each one costs a PDF parse, so it cannot be as loose as `/pdf/*`. The plugin is pinned to `caddy-ratelimit@v0.1.0` in `docker/web.Dockerfile`, and the limiter is ordered `before file_server` rather than `before reverse_proxy`, since the static server ranks earlier than the proxy and a limiter sorted after it never runs. Every zone is keyed on the visitor's IP as Caddy recovers it from `X-Forwarded-For`, which it believes only from `TRUSTED_PROXIES` (default `private_ranges`). A TLS proxy on a PUBLIC address must be named there, or every request appears to come from the proxy and the three per-IP limits collapse into three global buckets that one visitor can exhaust for everyone. All seven variables are read by the Caddyfile from `docker/.env` through the `web` service's `env_file`, and `docker/env.example` documents each.

The compose project is named explicitly (`name: ${SITE_ID:-justelesdocs}`), and `SITE_ID` also prefixes every container name (`<SITE_ID>-search`, `<SITE_ID>-pages`). Compose otherwise names a project after the directory holding the compose file, which is `docker/` here and in `../justelesRCP`, and both stacks define a service called `web`. Since Compose identifies a running container by its project and service labels, two stacks with the same project name are one project, and each deploy replaces the other's web container. Two sites on one host therefore need two `SITE_ID`s, and two `NETWORK_SUBNET`s (DESIGN.md, "Docker networking: pin the subnet").

`docker/entrypoint.sh` renders `/gen/app-config.js` from the environment, which is how the analytics settings and the dev banner reach the page. `docker/env.example` documents every variable; `docker/.env` is gitignored. The service reads `SEARCH_DIM`, `SEARCH_FLOOR`, `SEARCH_QUEUE_DEPTH`, `SEARCH_TEXT_CACHE` and `EMBED_URL` from that same file through compose's `env_file`, plus `INDEX_DIR=/index` and `SEARCH_PORT=8650`, which the compose file fixes because it is what decides those paths and ports.

The SEARCH container sits on the external Docker network `EMBED_NETWORK` (default `justeles-embed`), so `EMBED_URL` defaults to a container name, `http://justelesrcp-embed:8461`, resolved by Docker's embedded DNS. Nothing is published on the host by either side. The network is `external: true`, so compose neither creates nor deletes it and refuses to start when it is missing; a fresh host needs `sudo docker network create --subnet <a free /24> justeles-embed` once. With the optional `embed` profile (`docker compose --profile embed up`) the encoder runs in this stack instead, built from a justelesRCP checkout (`EMBED_CONTEXT`, `EMBED_MODELS`), and `EMBED_URL=http://embed:8461`.

Two host-based routes were tried first and neither can work, which is worth stating because both look reasonable: a port published on the host's 127.0.0.1 is unreachable from a container (the connection arrives from the bridge subnet, not from loopback), and compose's `ports:` accepts an IP and never a hostname, so `host.docker.internal` is rejected at parse time as a bind address. DESIGN.md, "Embedding service", has the full account. The consequence of getting it wrong is a site that comes up perfectly with a search box that 502s on every query, which the page shows as "search unavailable".

## Tests and gates, and how to run them

The test suite is one command, and it is the only check here that needs no corpus, no index and no browser:

```sh
uv run tests/run.py   # pytest over scripts/, node --test over src/, then $CORPUS_DIR/tests if set
```

It runs against `corpus.example/` and covers what can be checked from text alone, plus the service: the changelog parser, the manifest rules, the catalog generator, the bilingual string table, the query parser, `tests/load.test.mjs` for loading the index under node, `tests/service.test.mjs` for the HTTP surface and the queue (against a stub encoder over a real socket), `tests/test_stage.py` for what `stage.py` links into `dist/www/index/`, `tests/test_chunk_golden.py` pinning the chunk content hash and output, `tests/test_prepush.py` for the hook's refusal of a corpus file added anywhere in the pushed range (not only at its tip: a PDF added in one commit and deleted in the next is still in the history), and a syntax pass over every source file (`tests/syntax.test.mjs` parses each `.js`/`.mjs` under `src/`, `scripts/` and `server/` as a module, `tests/test_syntax.py` compiles every `.py` and runs `sh -n`/`bash -n` over the shell scripts and the hook), because most scripts have no other test and a stray bracket would otherwise surface only on the night one is run. `uv` builds the pytest environment on the fly, so a fresh clone needs no install step, and `.githooks/pre-push` runs the whole thing on every push. When `CORPUS_DIR` is set, the corpus's own `$CORPUS_DIR/tests` run after it. Everything that needs the corpus, the built index or a rendered page is a gate instead.

There is no linter. The gates all refuse rather than warn. The first three belong in the build chain, and `.githooks/pre-push` runs `verify_chunks.py` and `check_search.mjs` again on every push when `CORPUS_DIR` is set:

```sh
uv run scripts/verify_chunks.py   # the corpus: nothing skipped, no undrawable box
uv run scripts/check_served.py    # the staged tree: no restricted document, and no word of one
node scripts/check_search.mjs     # the shipped ranking, against a real dist/index/
```

`check_served.py` runs after `stage.py` rather than before, because what it watches is a property of the tree that was written, not of the code that wrote it. Only a machine-checked invariant makes "no restricted document is served" true of the next build too.

The next two need a browser and a served tree, so they are run by hand after touching `src/`:

```sh
REQUIRE_SEARCH=1 PW=<a playwright install> SITE=http://127.0.0.1:8649 node scripts/check_ui.mjs
PW=<a playwright install> SITE=http://127.0.0.1:8649 node scripts/check_chrome.mjs
```

What they expect of a particular corpus (example queries, documents to find) comes from `$CORPUS_DIR/scenarios.json`, read by `scripts/lib/scenarios.mjs`, with fallbacks derived from `meta.json` when it is absent.

`check_ui.mjs` exists because of one class of bug the other gates cannot see. It reads back the highlight rectangle the browser rendered, asks pdf.js which words fall inside it, and asserts those words belong to the passage being marked. Its first run found every highlight mirrored about the middle of the page: PyMuPDF's boxes are top-down, pdf.js's `convertToViewportPoint` expects bottom-up user space, and on a dense page a flipped box still has text under it, so it reads as a small offset rather than a flip. It probes `/api/search/health` first: with no search service it skips its search scenarios and says so, `REQUIRE_SEARCH=1` turns that skip into a failure, and a live service that returns zero rows is always a failure, because an empty result page is otherwise indistinguishable from a pass.

`check_chrome.mjs` covers `src/site.js`, the chrome every page carries: the development banner and the footer. Neither can be exercised against a deployed site, because both read `window.__APP_CONFIG__`, which the container renders from its environment, and the banner's rules are all time and storage rules. So the gate intercepts `app-config.js` per scenario and serves a synthetic one, and pins the browser locale to `fr-FR`, because `i18n.js` picks its default language from `navigator.languages` and an unpinned context silently checks English strings against French expectations.

`server/lib/browser_shim.mjs` serves `index/` off the filesystem through `globalThis.fetch`, so `src/search.js` runs unmodified in node; `server/load.mjs`, `check_search.mjs` and `evaluate_rescore.mjs` share it rather than each carrying a copy. `check_search.mjs`, `evaluate_rescore.mjs` and `sweep_blend.mjs` import the module directly and read `dist/index`: they measure the ranker, not the HTTP around it. `node server/load.mjs [dist/index]` is the smallest thing that exercises the service's own path, printing load time, rank time and RSS. `check_search.mjs` exploits the fact that queries and passages share one space: a passage's own stored row, unpacked by `chunkVector`, must retrieve that passage at rank 1. With `EMBED_URL` pointing at a running encoder it also puts real questions through the real wire format and prints the answers, which is the only way to see whether retrieval is any good.

To open the site locally, with search working:

```sh
cd ../justelesRCP && uv run src/embed-service.py --port 8461 --no-backlog   # the real encoder
EMBED_URL=http://127.0.0.1:8461 INDEX_DIR=$CORPUS_DIR/dist/index node server/service.mjs   # the ranker on :8650
PAGES_DIR=$CORPUS_DIR/dist/restricted INDEX_DIR=$CORPUS_DIR/dist/index uv run server/pages.py   # the cutter on :8651
uv run scripts/dev_server.py   # dist/www on :8649
```

A stale one of these is the trap worth naming: every service holds its port and none reloads on an edit, so a copy left running from a previous session answers with code from that session and every new launch fails to bind, in a log nobody is reading. `ss -ltnp | grep -E '8649|8650|8651'` and the start times it points at are the whole diagnosis.

The encoder may also answer at 8461 on the server, so `ssh -N -L 8461:127.0.0.1:8461 <the server>` is the other way to get one, and nothing else changes: the service's `EMBED_URL` and the pre-push hook both point at `127.0.0.1:8461`.

`dev_server.py` proxies the same four paths Caddy does: `/api/search` and `/api/search/health` to the ranker on `127.0.0.1:8650` (`--upstream`), and `/api/page` and `/api/page/health` to the page service on `127.0.0.1:8651` (`--pages-upstream`). It answers 404 for the rest, so a client-side mistake cannot look like a routing mistake. It embeds and ranks nothing itself: what the browser shows locally comes from the same ranker, index and encoder as on the server.

The last gate runs against a site that is already up, which is the one layer the others cannot see. A deploy script should pipe it over ssh at the end of every deploy, and it is runnable by hand against anything that serves this site:

```sh
sh scripts/smoke_deployed.sh http://127.0.0.1:8648   # on the server
sh scripts/smoke_deployed.sh http://127.0.0.1:8649   # against a local dev_server.py
```

It posts a real question to `/api/search` and checks that the answer holds results at the width `meta.json` was baked at, reads `/api/search/health` and checks the same width there (the two halves of `dist/` can only disagree if they came from different builds), checks that the vector files `meta.json` names answer 404 while `index/doc/0.json` answers 200, and checks that `/api/sem/embed` answers 404, since this site must not open a path onto the sibling's encoder. It also checks the access tier: it picks a restricted document out of the served `meta.json` and asserts that `/pdf/<its file>` answers 404 while `/api/page?doc=<its id>&p=1` answers 200. A 502 on the search is the exact failure a visitor sees as "the search service is unavailable", so the script prints the commands that separate "the encoder is not running" from "the search container is not attached to the shared network" from "EMBED_URL is wrong"; a 503 is the queue refusing; anything else is Caddy not reaching the search container.

## First deploy, step by step

Deployment is per corpus: the software ships no deploy script, and a corpus keeps its own (gitignored or in its own repository) that runs the build chain, transfers `dist/`, `docker/`, `server/`, the `src/` modules the search image copies and the root `.dockerignore` as an allow-list, then restarts the stack. Whatever the search Dockerfile copies has to be on that list, or the remote build fails on a file it cannot find.

Locally, once: build the chain (the README's quick start), and `cp docker/env.example docker/.env`, then edit it.

`SEARCH_DIM` used to be the one value in `docker/.env` that could produce wrong answers rather than a visible failure, because mismatched widths give meaningless scores rather than worse ones. It cannot any more: the search service compares it against `meta.json`'s `dims` at startup and REFUSES TO START when they disagree, saying so plainly, and the container restarts until the deploy fixes one side. Left unset, the service trusts the width the index declares. Set it anyway: a refusal at startup is the failure you want.

It does not have to equal the encoder's own default width. `embedQuery` sends `dim` in the POST body and the shared encoder truncates the query vector to it, so two projects can bake at different widths against one model. A `dim` it cannot serve is a 400, and a reply at any other width is refused by the service before ranking.

On the server, create the shared network once and check that the encoder is on it. This is the one part of the deploy that is easy to get wrong and gives no error until a visitor types a question:

```sh
sudo docker network create --subnet <a free /24> justeles-embed
sudo docker network inspect justeles-embed --format '{{range .Containers}}{{.Name}} {{end}}'
```

When something on that host cannot reach the network at all, `scripts/diagnose_network.sh` collects the whole picture into one redacted report (`ssh <the server> 'sh -s' < scripts/diagnose_network.sh > diagnostics.log 2>&1`) and ends with the two findings that actually strand a container: a Docker bridge outside RFC1918, and a bridge subnet that overlaps one of the host's own routes. Both happen on a host running many stacks, because Docker's default address pool is finite and a newly created network takes whatever is left.

Both the encoder container and `<SITE_ID>-search` have to appear in that list. If the encoder is missing, deploy justelesRCP, whose compose file attaches its embed service to this network, or use the `embed` profile. A `curl` from the host proves nothing here, since nothing is published on the host; the question is only ever what the container can resolve and reach.

The first `up` needs the web image built (`sudo docker compose up -d --build`): it is an xcaddy build of Caddy plus the rate-limit module, and the one step that needs outbound internet on the server. Later deploys reuse it. A change to the `order` line or to the `per_ip_limit` snippet in `docker/Caddyfile` needs no rebuild (the file is bind-mounted) but does need a restart, and Caddy refuses to start on a config it cannot parse: watch that first restart rather than assuming it came back.

The site then answers on `127.0.0.1:8648` on the host, plain HTTP, for the reverse proxy that terminates TLS to forward to. `BIND_ADDR` in `docker/.env` widens that, and the default (loopback) is the safe one. The search container publishes nothing, so the only way to see it from the host is `sudo docker compose ps` and its own health check.

`APP_UID` and `APP_GID` are the other two values to set on a first deploy: all three containers run as that uid:gid, so they read the host-owned mounts as the deploying user rather than as root. They default to 1000, which is often wrong on a server, so take them from `id -u` and `id -g` there.

What to check after the first run, in this order, because each answer narrows the next: `/index.html` loads, the search container is healthy (`sudo docker compose ps`, and `sudo docker exec <SITE_ID>-search wget -qO- http://127.0.0.1:8650/api/search/health`), a search returns hits (that exercises Caddy's proxy to the service, the service's reach to the encoder, and so the network setup), and a hit opens on a PDF page with the passage highlighted (that exercises `dist/www/pdf/` having arrived as real files rather than dangling symlinks, which is what `rsync -aL` is for). `scripts/smoke_deployed.sh` is the scripted form of that list.

## The constraint that shapes everything

Only `$CORPUS_DIR/data/GUIDELINES/` may be served, indexed or shipped. A corpus directory may hold other documents (rejected, unsure, not redistributable), and none of them may ever leave the build machine. Every script takes that directory as an explicit root, `dist/` is built by a script rather than by rsync include rules, and `.dockerignore` denies everything before re-admitting `docker/`, `server/` and named modules of `src/`. The whole build is an allow-list, in each of the three places where a mistake would ship a document that must not leave the machine. The pre-push hook refuses to push a corpus file.
